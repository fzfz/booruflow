# インターフェース操作規則

本規則はすべての画面に適用します。各画面仕様は本ファイルを参照し、本規則が優先することを宣言します。画面仕様には、実在する要素、配置、操作と API の対応、画面固有状態、受入操作だけを定義します。矛盾がある場合は、実装前に画面仕様を修正します。

## 1. 用語

クリック可能な要素には `button`、`a`、明確なキーボード操作を持つ選択項目を使います。1 回の要求操作は、1 つの利用者意図と 1 回の HTTP 要求に対応します。「処理中」は要求を送信してから利用可能な応答を受け取るまでの状態です。「成功」は契約どおりの HTTP 状態と `ok:true` を受け取った状態です。「失敗」には失敗を表す HTTP 状態、`ok:false`、不正な応答、ネットワークの中断、ローカルでの取消を含みます。「選択済み」は画面が対象を採用した状態であり、「草稿」はフロントエンドだけに存在するデータです。現在の対象を識別する値は要求が完了するまで変更しません。

## 2. 表示状態

`idle` は 1 回の操作を許可します。`disabled` は、ネイティブの `disabled` 属性、無効であることを示す表示、対応する ARIA 状態を同時に設定し、マウス、キーボード、リクエスト送信を無効にします。処理中は対象と操作名を表示し、既存内容を残して再送信を禁止します。`selected` は、`.is-selected` の表示と、適用できる `aria-selected` または `aria-pressed` を同時に設定します。成功時はレスポンスの値で内容を更新して短く通知し、失敗時は直近の成功内容を保って具体的な理由を示します。文言、色、無効属性、ARIA は同時に変えます。文言変更でボタン位置を動かさず、失敗後は入力、選択、スクロール位置を保持します。

## 3. ボタン、クリック、要求ロック

操作には実際の `button`、遷移には `a` を使います。1 操作につきイベント入口を 1 つにし、`event.target.closest('[data-action]')` で対象を得ます。マウス、Enter、Space は同じ操作とロックを共有し、空白、文言、アイコンのどこからでも 1 回だけ動作します。危険操作は確認層を先に開き、確認ボタンだけが要求を送ります。取消、閉じる、戻る、背景クリックは業務書込を送りません。

業務リクエストを送る各非同期関数は、独立した `isSubmitting` を持ちます。値を検証してからロックを確認し、ロック中であれば直ちに終了します。ロックされていない場合は、送信前に値を `true` にしてボタンを無効化し、リクエストを 1 回だけ送信します。成功時はレスポンスに基づいて画面を更新します。バックエンドのエラー、タイムアウト、ネットワークエラー、解析エラー、その他の終了エラーが発生した場合は、具体的な理由を示します。成功と失敗のすべての終了経路で `isSubmitting` を `false` に戻し、現在の画面に残っているボタンを現在の状態に従って復元します。画面遷移によってボタンが削除された場合も、処理関数が保持するロックを解除します。自動では再試行しません。処理終了後に利用者が再試行した場合だけ、リクエストを 1 回送信します。画面内だけで完結する操作はリクエストを送りません。読み取り、作成または更新、削除、バッチ、確定した検索、ファイルのバッチ操作は、成功時も失敗時もリクエストを 1 回だけ送信します。検索文字の入力、削除、消去ではリクエストを送らず、1 つのバッチ処理を項目ごとのリクエストへ分割しません。

## 4. 選択、取消、順序

妥当性確認後に選択集合と表示を直ちに更新します。同じ `kind:id` は 1 件だけ保持し、送信時は完全な集合を渡します。`selection_order` は 0 から連続し、欠番、負数、重複を許しません。上限時は追加を無効にして上限を表示します。取消ボタンは対象名または `aria-label="{名称}を削除"` を持ち、パネルを閉じても選択を保持します。

`kind` には、API が許可する `work`、`character`、`style` の集合を使います。`id` には 1 以上の安全な整数を使い、`selection_order` は 0–29 の範囲にします。上限は作品 5 件、キャラクター 20 件、画風 10 件、合計 30 件です。バックエンドは、送信された完全な集合について、存在、利用可能性、型を再検証します。

## 5. フロントエンド検証

利用者が入力したテキストは、検証済みの元の業務値として保存し、HTML エンティティへの変換や逆変換を行いません。プレーンテキストは `textContent` で表示し、固定された `innerHTML` 内の動的な値は、文脈に合わせてエスケープします。契約で定めた長さを適用し、指定がある場合は Unicode コードポイントを数え、Unicode の規則で空白を判定します。検索文字列は両端の空白を除き、連続する空白を 1 個にまとめ、空の検索を送りません。

リソース ID と画像 ID には安全な正整数を使います。パスに含まれる ID の元文字列を `^[1-9][0-9]*$` で検証し、数値への変換後に `Number.isSafeInteger(value)` と契約上の上限を検証します。小数、負数、空文字列、指数表記、余分なパスを拒否します。数値項目は数値として送り、`NaN`、`Infinity`、小数の ID、安全な範囲外の値を拒否します。要求オブジェクトには必須項目をすべて含め、未知の項目を含めません。契約が許可する場合だけ `null` を送り、`undefined` は直列化せず、配列の各要素を検証します。リポジトリ層は SQLite のパラメーター結合を使い、動的な並べ替え条件は検証済みの列挙値から固定 SQL へ対応付けます。

## 6. バックエンド検証

HTTP メソッドとパス、`Content-Type`、JSON の解析結果、通常のオブジェクトであること、必須項目と未知項目、型、長さ、列挙値、範囲、配列の重複・欠番・上限超過、パスの ID、対象の存在・型・利用可能性、完全な選択集合の順に検証します。すべての検証を通過した後に限り、データベースへの書き込み、メディア処理、ベクトル処理、ComfyUI の呼び出しを許可します。パス、クエリー、ヘッダー、Cookie、JSON、multipart の値はすべて未信頼の入力として扱います。

利用者の入力内容は契約に沿って検証し、明示的に正規化します。操作の意図について、範囲、一意性、所有関係、関連、状態を検証します。権限、所有者、状態、件数、`attempt_no`、時刻はサーバーが取得し、公開された書き込み要求からは受け取りません。`impact_token` などのサーバー発行値は、OpenAPI が定義した用途に限って返送できます。サーバーは、その値の存在、所有者、用途、現在の状態を再確認します。有効期限や一度限りの利用は、契約に定義がある場合に検証します。

## 7. 要求と応答のライフサイクル

送信前に現在のフォームを読み取って検証し、第 3 節の規則に従ってロックと無効化を行います。リクエスト中は直近の成功内容を残し、送信値を局所変数に保持します。同じ対象の編集を無効化し、無関係な領域は利用可能なままにし、処理中表示は 1 つだけ表示します。ダイアログを閉じても、送信済みの業務リクエストは取り消しません。成功時は 1 つのレスポンスを使って対象、一覧、件数、選択、文言を更新し、2–3 秒間通知します。ロックと操作部品は第 3 節の規則に従って復元します。必須のレスポンス項目が欠けている場合は構造エラーとして扱います。失敗時は直近の成功データと入力を保持し、一時的な処理中表示、仮の選択、仮の順序を消します。`error.code` に従って再試行手段を配置し、推測した題名、順序、カバー、一覧を設定しません。

## 8. 共通エラー処理

コードと文言は `schema/api/error-catalog.json` と画面規則から取得します。画面に表示する各エラーは、結果、影響を受ける項目・ボタン・記録・ファイル・一覧、利用者が次に行う操作、現在のデータが保持されているかどうかを説明します。エラーは影響を受ける領域に表示し、元のコードは折りたたみ式の詳細欄に表示できます。`Error`、状態コード、`undefined`、空白だけの文言は表示しません。

## 9. 応答の整合性

JSON は `{"ok":true,"request_id":"...","data":{}}` または `{"ok":false,"request_id":"...","error":{"code":"...","message":"..."}}` の形式です。`request_id` は、バックエンドが今回の要求とログを関連付けるためだけに生成します。フロントエンドはこの値を生成せず、タスク ID、再入防止トークン、冪等性キーとして扱いません。HTTP 状態、JSON であること、状態と一致する真偽値 `ok`、空でない `request_id`、成功時の `data` または失敗時の `error.code` と `error.message` の順に契約を検証します。

## 10. 利用者が対処できるエラー

項目のエラーは、安定した ID、`aria-invalid`、`aria-describedby` を使って項目の直下に表示します。入力内容は消さず、利用者が修正した直後にエラーを除きます。項目、パネル、権限に関するエラーは、問題が解決するまで表示します。ネットワーク状態の全体表示は 3 秒後に消せますが、操作箇所の近くにあるエラーは残します。未知のシステムエラーの全体表示は 5 秒後に消せますが、ログは残します。トースト通知は補助としてだけ使います。要求が失敗した場合は処理中表示を除き、再試行できる操作部品とデータを元に戻します。エラーコードを文言へ変換して次の操作を示し、操作名、対象キー、時刻を記録します。`VALIDATION_ERROR` では項目の修正、`ITEM_UNAVAILABLE` では失効したことの表示と再選択、`NOT_FOUND` では一覧へ戻る操作、`WRITE_FORBIDDEN` では書き込み操作の無効化、`DATABASE_BUSY` では後から手動で再試行する方法を案内します。`UPLOAD_TOO_LARGE` と `UPLOAD_TYPE_UNSUPPORTED` ではファイル名と制限を示します。`INTERNAL_ERROR` では現在のデータを保持し、後から手動で再試行できるようにします。

バッチ処理は成功と失敗を項目別に表示し、成功した結果を保持して失敗理由を残し、失敗した項目だけを再送します。失敗後のフォーカス移動には、第 12 節の規則を適用します。全体エラーには `role="alert"`、通常の成功通知には `role="status"` を使い、同じエラーについては既存の要素を更新します。折りたたみ式の詳細欄にはコード、操作名、クライアント時刻を表示できますが、主画面にはスタックトレースを表示しません。

## 11. 並行要求

同じ対象の同じ操作は直列にします。異なる対象は独立した非同期関数で並行処理でき、各関数は対応領域だけを更新します。遅れて届いた古い応答は新しい現在対象や一覧を上書きしません。

## 12. フォーカス、キーボード、スクロール

初回読込後は、最初の主要操作または入力欄へフォーカスを移します。ダイアログを開いた場合は、閉じるボタンまたは最初の操作へフォーカスを移し、背景のスクロールを固定します。Esc キーは最上層だけを閉じ、確認画面を優先します。閉じた後は、開始ボタンへフォーカスを戻し、元のスクロール位置を復元します。Tab キーでは、表示中で有効な操作部品だけを移動対象にします。検索結果の更新後は検索欄のフォーカスを保持し、選択後はスクロール位置を保持します。入力項目の検証エラーでは、最初の誤りがある項目へフォーカスを移します。その他のリクエスト失敗では、利用可能な再試行、再読込、または元の操作部品へフォーカスを移します。利用可能な操作部品がないエラーでは、エラー領域へフォーカスを移します。

## 13. 読込、空、失敗状態

各データ領域には、読込中、データあり、空、読込失敗の状態を個別に実装します。読込中はスケルトン表示または文言を示し、同じデータを変更する操作を無効化します。空の状態では理由と次の操作を示し、失敗状態では理由と「再読込」を示します。局所的な失敗は、その領域だけを置き換えます。利用者が再読込を選んだ場合は GET 要求を 1 回だけ送り、終了するまで追加のクリックを無視します。

## 14. ファイルアップロード

少なくとも 1 個のファイルを選択した後、一覧へ表示する前に `config/defaults.json` の `uploads.allowed_media_types`、`uploads.max_file_bytes`、`uploads.max_files_per_request` の現在値を読み取ります。その値を使って、メディア種別、各ファイルの大きさ、バッチ内のファイル数を検証します。不正なファイルについては名前と理由を示し、条件を満たすファイルは続けてアップロードできるようにします。1 回のクリックにつき multipart 要求を 1 回だけ送り、処理中は同じバッチの操作部品を無効化します。成功時はサーバーが返した画像 ID と順序に従って画像一覧を更新します。失敗時は元の画像一覧を保持し、ID を生成しません。並べ替えでは、完全な `image_ids` を 1 回の PUT 要求で送ります。カバーの指定には 1 つの `image_id`、または契約が許可する `null` を使います。

## 15. 状態フック

HTML では、操作に `[data-action]`、対象に `data-item` または `data-image-id`、処理中の状態に `aria-busy` または固定された要素、エラーに `role="alert"` または `aria-describedby`、成功と進行の通知に `role="status"` を使います。選択状態と無効状態の表示、ネイティブ属性、ARIA の同期には、第 2 節の規則を適用します。

## 16. 分岐受入条件

各画面で実際の操作を確認します。空の値では要求が 0 回であり、有効な値では正しい HTTP メソッド、パス、本文、件数を使うことを確認します。二重クリックでは、要求、処理中表示、更新がそれぞれ 1 回だけ発生することを確認します。マウス、Enter キー、Space キーでは同じ操作が実行されることを確認します。失敗時はデータ、入力、選択を保持して操作部品が元に戻り、成功時は応答データを使用し、古い応答が新しい状態を上書きしないことを確認します。不正な型、範囲外の数値、未知の項目、重複した配列を受け取った場合は、書き込みや上流サービスの呼び出しを行わずに `422 VALIDATION_ERROR` を返します。権限不足、対象なし、利用不可の各エラーが適切な位置に表示されることを確認します。390×812、768×1024、1440×900 の各表示領域で、フォーカス、スクロール、ドロワー、半画面パネル、固定入力領域を確認します。

## 17. 実装根拠

HTTP メソッド、パス、要求、応答は `schema/api/openapi.yaml`、エラーは `schema/api/error-catalog.json`、アップロード制限は `config/defaults.json` を唯一の情報源とします。画面固有の文書は本規則を参照し、その画面に固有の事実だけを追加します。現在の実装とテストによって、バックエンドの入力検証を確認します。
