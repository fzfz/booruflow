# CI/CD ゲート

## コードをマージする

貢献者は PR を通じて変更を `main` にマージします。GitHub の `main CI gate` ルールは、ブランチが最新のメインブランチに追従していること、レビューの議論が解決済みであること、GitHub Actions の `CI Gate` 検査が成功していることを要求します。この検査は Windows、macOS Apple Silicon、macOS Intel のテストとプラットフォーム間のデータ交換結果を集約します。前提となるジョブが失敗、中止、スキップのいずれかになると、ゲートは失敗します。

他者による必須承認数は 0 件です。単独の管理者も自分の PR をマージできます。管理者は引き続き [PR 規約](../community/pull-requests.md)に従って変更を確認します。ルールは管理者にも適用され、線形の履歴を要求します。squash または rebase でマージし、メインブランチを保持して、新しいコミットで問題を修正してください。

## バージョンを公開する

管理者は[リリース手順](releases.md)でバージョンを準備し、PR を通じて変更をマージしてからバージョンタグを作成します。`Release checks` は、タグの形式、タグのコミットが `main` に含まれること、パッケージのバージョン、インストーラーの既定タグ、データパッケージのアプリバージョンの一致、および `docs/releases/vX.Y.Z.md` の存在を確認します。管理者は[リリース手順](releases.md)のリリースノート要件に従ってこのファイルを作成します。公開スクリプトはファイル全体を GitHub の説明として送信します。

`Release Gate` は、事前検査、3 プラットフォームのテスト、実際のタグのインストールテスト、データ交換がすべて成功することを要求します。その後、公開ジョブは `github-release` 環境に入り、`fzfz` が GitHub Actions でタグ、コミット、検査結果を確認して承認するまで待機します。承認後、ジョブはドラフトを作成し、`install.bat` と `install.sh` を添付してから公開します。通常のブランチで手動実行した場合は検査のみを行います。

公開済み Release は保持します。アップロード失敗でドラフトが残った場合、管理者はその未完了ドラフトを確認して削除してから失敗したジョブを再実行します。スクリプトは既存の Release の上書きを拒否します。`immutable release tags` ルールはすべての `v*` タグと参照先を保持します。修正版には新しいタグを使います。環境の承認は Actions の公開ジョブに適用されます。リポジトリ管理者は設定の変更や Release の手動操作を行うことができます。

## 失敗を確認する

PR ページには `CI Gate` が表示されます。Actions の `Platform checks` で各プラットフォームの詳細を確認できます。公開に失敗した場合は、`Release checks` の失敗したステップを調べ、問題を解決して再実行します。テスト範囲とカバレッジの受け入れ要件は[テスト](testing.md)を参照してください。
