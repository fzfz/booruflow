# Issue workflow

The repository provides bug, support, and feature templates in four languages. Bugs require version, system architecture, installation method, reproduction, expected and actual results, output, and a minimal example. Support requests require a goal, blocked step, and attempted checks. Features require a use case, desired behavior, and limitations of the current method. Replace secrets, credentials, and personal paths.

Maintainers use structured labels for these states:

- **Needs triage:** type and evidence remain to be assessed; leave after classification.
- **Needs information:** required reproduction or decision evidence is missing; leave after the reporter supplies it.
- **Confirmed:** the problem or goal can be reproduced and assessed; leave when implementation starts.
- **In progress:** an owner and concrete work exist; leave after a fix or decision.
- **Resolved or closed:** a version or procedure has been supplied and confirmed, or the duplicate, out-of-scope, or unreproducible reason is recorded.

Questions must list exact gaps. Reassess after each response. A fixing PR links the issue; after merge or an actionable resolution, record the version and verification before closing.
